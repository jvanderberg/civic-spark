# Workspace Sprite lifecycle

Event admins manage their event's workspace Sprites in a compact list with owner/team, status, elapsed runtime, one estimated cost, and individual Pause/Delete actions. Retained reservations after membership/team removal remain visible. Provider observations and portal activity metadata remain available through the authorized inventory API; the list avoids repeated metadata panels. It never exposes another participant's files, keys, conversations or provider command details. Metadata refresh uses named provider GET requests and does not execute workspace commands.

## Pause and resume

**Pause** durably holds, drains and stops only the selected workspace. **Pause all Sprites** durably holds the event's currently allocated workspaces and interrupts their managed work. An owner can reload to resume the same reserved Sprite. **Pause hackathon** first commits an event-wide execution gate, then holds and stops allocated workspaces. The gate survives restart and rejects provisioning, wake, execution HTTP routes, agent/terminal sockets, preview management actions and integration callbacks. Unpause removes the event gate; it does not start every Sprite. Owners resume on demand.

Stops cancel and drain in-flight management commands and provisioning jobs, close agent/terminal bridges, stop the native public preview service through the provider. Historical retired preview origin assignments remain unchanged. Failed or interrupted stops keep the gate and display a retry. EventService validates event-admin writes; owner access, existing memberships, origin checks and verified/demo/prototype identity separation remain authoritative. A fabricated Upgrade header cannot bypass the HTTP gate.

The paused event remains available for portal browsing and **shared** team repository downloads, which are built from persisted canonical Git without a Sprite. Private workspace reads/writes are blocked. Event configuration, roles, membership cleanup and explicitly authorized shared-repository administration remain available: this is an execution pause, not a database freeze. No prototype-store fallback, automatic Share or private-source export is added.

## Individual deletion

**Delete** requires event-admin confirmation that unshared private Sprite files, saved keys and conversation history will be lost. Shared Git, accounts, event/team memberships, project catalog and the stable owner workspace ID remain. The selected Sprite's runtime identity is retired; a later owner connection uses a new random Sprite name and therefore a new native preview URL. Historical retired preview-origin ledger entries are retained as non-reusable tombstones.

The session/admin/origin-validated action includes the expected lifecycle generation. EventService advances that generation and commits a provider-bound pending deletion gate before disconnecting agent/terminal/integration bridges, cancelling command leases and draining entire HTTP requests, queued relay operations and provisioning starts/jobs. The event operation lock serializes individual/bulk actions. Revalidation after draining prevents a stale confirmation from deleting another generation. Agent output and deferred relay callbacks from removed sessions cannot reattach or modify the replacement; team-status caches include the generation.

The provider adapter first authenticates the organization and verifies the exact named resource using the same strict ID/name/organization/list-witness rules as restored-resource recovery. Fresh authenticated exact404 is already absent and needs no DELETE. Otherwise DELETE must return 204 or 404 **and** a new authenticated inspection must confirm exact404. A surviving resource, contradictory list witness, invalid identity, auth failure, network failure, timeout or any other DELETE response leaves the old reservation and metadata intact behind a retryable hold. No provider diagnostics/private content are returned. Restart marks a pending action failed without contacting the provider; retry uses the original organization/origin.

The provider adapter rechecks current admin authorization and the held workspace generation after all identity preflight awaits, before accepting an already-missing result or dispatching DELETE. Revocation or a newer generation at that boundary leaves the original metadata held and sends no DELETE. Once an authorized DELETE has been dispatched, later admin revocation does not prevent absence confirmation and cleanup; the final generation check still prevents cleanup from touching a newer runtime.

### Metadata lifecycle

1. Before confirmed absence: retain Sprite identity, initial-creation evidence, provisioning phases/errors, checkout-repair and restore evidence, integration tickets and private state. Only the generation and deletion gate change. Uncertain outcomes never authorize reset or recreation.
2. After confirmed absence: persist a short deletion receipt containing the retired name and a generated replacement name. While this receipt is held, remove just this workspace's obsolete restore-recovery entry and agent integration conflict ticket. Clear the engine's Sprite name/status/error/phase/timestamp/creation-failure fields and initial-creation reservation. Replace runtime state with defaults, an advanced monotonic generation, an explicit-connect hold and a small `reset` record containing the new name and provider organization/origin. Old stop/idle timestamps, stop errors, checkout-repair intent and deletion/replacement flags disappear. Native saved keys, agent provider session IDs/history, terminal tmux, Tasks/processes and connection configuration lived on the deleted Sprite; management replay/bridge state is disconnected, never copied. No new resource is allocated at this point, and the old inventory row disappears.
3. Cleanup writes span the prototype's stores. The durable confirmed receipt precedes cleanup and remains until every cleanup step succeeds. Restart repeats this idempotent **local-only** cleanup; it does not issue DELETE or create. A pending/uncertain receipt instead remains a retryable failure. Persistent cleanup/storage failure fails startup closed for operator repair. This is scoped crash reconciliation, not a general cross-store transaction system.
4. The owner explicitly chooses **Connect new Sprite** (or calls the authorized wake/preparation API with `action: "connect-new"` and the current reset generation). Old ordinary wake/automatic preparation requests cannot authorize this transition. Event pause still blocks it. The fresh-name `reset` record routes preparation through authenticated resource inspection and **canonical shared `main` only**, never the retained prototype private checkout. Normal provisioning concurrency limits apply. Generation/access/provider checks repeat after asynchronous work, including owner session and membership revalidation after admission to the real create queue and before POST. Partial preparation retains the new identity and shared-only intent for safe retry; an existing verified private checkout is preserved, and uploads require an absent project. Only verified ready clears `reset`. Failed preflight restores the connect hold. Polling, inventory, reload and startup do not recreate a deleted Sprite.

Reset persistence uses merge-based `setRuntime`: `runtimeSchema.parse({})` supplies explicit `deletion: null` and null stop/activity fields, so the old deletion object (including nested `reset`, `ownerRecovery` and replacement flags) is replaced wholesale. Optional `projectRepair` is explicitly overwritten with `undefined` and omitted from stored JSON. Optional top-level `reset` is deliberately overwritten with the newly reserved name/provider binding, then explicitly cleared with `undefined` only after verified ready. The restart regression seeds an old top-level reset, repair intent and nested deletion qualifiers, interrupts cleanup, and checks the exact persisted default state plus the new connect intent after restart.

Shared Git and publication bookkeeping/history are preserved, including any explicit Share already committed before the deletion gate. Deletion never Shares private work or migrates account data. Old local prototype files are preserved on disk but cannot seed the fresh Sprite. Other workspaces' metadata, reservations, recovery entries and resources are untouched.

Existing restored/missing-resource owner recovery is separate: it retains its verified reserved name and demands its existing explicit authorization/evidence. Absent-checkout repair also stays on the existing verified Sprite. Admin Delete is the deliberately destructive escape hatch; it does not relax either identity contract.

## Provider mechanics and limits

Reviewed official documentation on **2026-09-16**. The [Sprite API](https://docs.sprites.dev/api/v001-rc48/sprites/) exposes status and creation/update metadata but no manual VM suspend operation. Its update endpoint changes URL settings. Civic Spark uses supported [service stop](https://docs.sprites.dev/api/v001-rc48/services/) and [exec kill](https://docs.sprites.dev/api/v001-rc48/exec/) operations, plus a fixed remote maintenance script to stop the managed tmux workloads and release the browser agent activity hold. It never deletes a Sprite, changes identity, rewrites Git or resets saved credentials as a pause shortcut. Already sleeping Sprites are left asleep.

Provider status is separate from “access paused.” Sprites normally suspend after about 30 seconds without provider activity. Warm sleep retains memory; cold sleep retains disk but loses processes, so shell memory and unsaved running-program state are not guaranteed. Saved source, Git, credentials and persisted provider conversation/context remain. See [lifecycle and persistence](https://docs.sprites.dev/concepts/lifecycle/).

There is no provider-wide deny-wake control in this implementation. External organization-token holders, directly exposed Sprite URLs and unmanaged detached work are outside the portal gate. Unknown activity holds cause stop failure, not a false success. Native hibernation can wake existing services; an explicitly stopped preview required Launch in dedicated provider testing. Dedicated preview service stop/start was verified separately below; complete admin-pause and quiet hibernation acceptance remain unverified. Portal pause alone does not establish zero charges.

## Inactivity

`CIVIC_SPARK_WORKSPACE_IDLE_MINUTES` is a setup-level integer from 1 to 120, default **5**. A 15-second management timer releases inactive platform polling and connections; it does not compete with provider VM sleep. Trusted participant input records portal use. Status polling does not. Actual pending/active browser model turns, preparation, in-flight operations and recent terminal **input** delay release. Terminal output never counts: tmux status refreshes and TUIs emit indefinitely, and an attached tty stream is provider activity, so counting output kept a Sprite in billed running state for hours (observed 2026-09-18). Typing in the terminal records workspace activity like other participant input, so an open terminal survives while the person is active anywhere in the app. Public native preview traffic bypasses management; it follows provider activity/billing semantics. At management idle release, workspace execution APIs are held and subsequent preview status polls cannot run Sprite exec. Agent/terminal/integration bridges detach, preserving remote services and tmux for native hibernation and later public visits. No periodic management restart or wake is scheduled. A quiet provider service is [documented not to keep the VM active](https://docs.sprites.dev/concepts/services/#services-and-the-sprite-lifecycle); actual no-traffic hibernation and later wake still require dedicated acceptance. Active public visitors may keep it awake and incur usage.

Browser model turns acquire a [Tasks API hold](https://docs.sprites.dev/keeping-sprites-running/) with five-minute expiry and one-minute renewal, released at completion. Stop during hold acquisition cannot start a late paid turn. An idle runner has no hold. This follows the provider's documented heartbeat default. Arbitrary silent background programs/native terminal agents are not automatically instrumented with Tasks holds; their completion depends on provider activity detection or an explicitly managed task. Cold sleep can lose their process state. Recent terminal output is activity, not proof of a browser model turn.

## Cost display

[Official pricing](https://fly.io/sprites/#pricing), retrieved **2026-09-16**, USD: CPU $0.07 per CPU-hour, actual memory $0.04375 per GB-hour, hot storage $0.000683 per GB-hour, cold storage $0.000027 per GB-hour. Sleeping compute is not charged, but persisted storage can be. Provider GET metadata does not supply cumulative CPU, memory/storage usage or active-duration history.

The product displays one **Estimated cost** amount and a separate runtime duration, without cost prose, tooltips, formulas or disclosures. Per the requested approximation, runtime is elapsed time since provider `created_at`, assuming continuously up. The best-guess workload uses the official pricing page's coding example: average **0.6 CPU, 1.5 GB memory, 5 GB hot storage and 10 GB cold storage**, totaling **$0.11131/hour** at the rates above. This is an estimate rather than measured billing; model charges, plan allowances and other hosting are excluded. Missing/invalid/future start timestamps display a dash. Reset Sprite rows disappear from allocated inventory; no ongoing runtime/cost estimate is shown for them.

Setup-wide overrides are `CIVIC_SPARK_ESTIMATE_CPU`, `CIVIC_SPARK_ESTIMATE_MEMORY_GB`, `CIVIC_SPARK_ESTIMATE_HOT_STORAGE_GB`, and `CIVIC_SPARK_ESTIMATE_COLD_STORAGE_GB` (finite nonnegative numeric units, maximum 10000 each). There are no per-team knobs. Only these operator docs describe assumptions; routine product rows contain the currency amount alone. No invoice or secret access is required.

## Recovery and portability

`SpriteLifecycleProvider` separates provider inspection/stop/destruction from durable event policy. `CIVIC_SPARK_SPRITE_API_URL` selects the authenticated HTTPS metadata API; execution uses the configured Sprite CLI organization and token. Replacing the execution provider requires its adapter, not a Fly Machine stop call. No private-network assumption is introduced.

The [backup/restore workflow](backup-restore.md) captures `event_execution` and `workspace_runtime` in access.sqlite. Restore remains fenced until explicit operator reconciliation validates installation/provider identity and records exact authenticated 404 evidence. Only an explicit authorized owner reopen can use that marker. Provisioning rechecks the same name immediately before creation and honors event pause before and after the check. A missing Sprite is recreated under its existing reserved name from canonical shared Git; workspace/user/team identity and permanent preview origin remain. A surviving Sprite is reattached without replacing its private project. Auth/network/provider errors never authorize recreation. The marker remains through failure and is consumed only after ready verification. No automatic startup provisioning or publication occurs. Unshared Sprite state is intentionally outside disaster recovery.

### Exec-list compatibility correction

September 16, 2026 dedicated live acceptance found that `GET /v1/sprites/{name}/exec` returned HTTP 200 with `{count, sessions}`, while the public API reference illustrates a bare array. The stop adapter now accepts both shapes and validates every session ID before issuing any kill requests. It does not treat `is_active: false` as proof that a process has exited. Malformed envelopes still fail closed. The dedicated probe separately confirmed an empty services array, available tmux and an empty Tasks list; kill-response and end-to-end stop acceptance remain a separate live verification after integration. This correction was developed using isolated mocks, without provider calls.

Correction validation: focused provider/lifecycle tests passed 19 tests; `npm run check` passed 246 tests in 47 files, lint, both typechecks and production build. No UI behavior changed.

## Owner-confirmed missing workspace recovery

Failed legacy reservations can enter the existing durable replacement lifecycle through EventService's validated `confirmMissingWorkspace` operation after explicit owner confirmation and fresh authenticated exact404 evidence. The `ownerRecovery` qualifier records current absence with name/account binding; it does not manufacture a DELETE receipt or initial-create evidence. This path never calls DELETE and fails closed for any present resource. Replacement remains reserved through failure; ordinary wake/polling cannot create it. A confirmed retry repeats provider/access checks and restores only canonical shared Git. Admin deletion/reopen behavior remains separate. HTTP, actual queue-dispatch, delayed-response and shared-only regressions are in `tests/missing-workspace-recovery.test.ts`; confirmation/cancel/reload interactions run in the provisioning/mobile browser matrix.
