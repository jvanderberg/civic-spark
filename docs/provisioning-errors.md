# Workspace provisioning errors

Token-configured installations create Sprites through one authenticated HTTPS `POST /v1/sprites`, using the configured API origin and the token's validated organization. The response must identify the requested name and organization. There is no automatic POST retry, redirect, or CLI fallback after an ambiguous result. Command and lifecycle admission remain bounded; checkout and participant execution still use the existing CLI inside the reserved Sprite.

Local installations with only a saved CLI login retain the pinned `create --skip-console` path. Free-form stderr is not a structured provider contract: CLI failure is sanitized to unknown, even if its text mentions a limit, HTTP status or credential. No error body, stdout, stderr, provider message or upgrade URL is persisted or returned to the browser.

The [official Go SDK error schema](https://github.com/superfly/sprites-go/blob/main/errors.go), checked 2026-09-17, supplies `error` as a string, with separate `concurrent_sprite_limit_exceeded` and `sprite_creation_rate_limited` codes. The adapter consumes those exact codes from a bounded JSON response. The first means provider capacity, including concurrent active-workspace restrictions; it does not identify a particular running/warm/total quota. The second means creation throttling. No separate running/warm error codes or prose patterns are invented. Both may use HTTP429; an unknown structured code remains unknown. Bare429 gets a generic request-limiting message. HTTP401/403 indicate access denial; HTTP408/5xx and transport failures indicate a connection/service failure with an uncertain creation outcome. Successful HTTP with malformed, oversized or mismatched identity data also remains uncertain.

The provider's [API reference](https://sprites.dev/api/sprites) documents creation, named-resource GET and list metadata's `running_limit`/`warm_limit`. Limit values or resource counts alone do not establish why an earlier creation failed. This change does not assert quota for any historical incident whose original diagnostics were discarded.

`spriteCreationFailure` stores only an optional allowlisted category in the existing workspace state. Domain writes preserve the first observed category through phase changes, retry failures and restarts. Successful preparation clears it. Legacy records receive no inferred cause. If recording an error fails, the already-persisted reservation still prevents a second allocation; the lost cause cannot be reconstructed.

A failed reconnect may perform a bounded metadata GET for the exact reserved name. Only HTTP404 establishes current absence; access errors, timeouts, malformed responses and identity mismatches remain unknown. Neither absence nor uncertainty authorizes a create or replacement. Existing explicit admin-deletion/backup-recovery authorization is unchanged. Current failure copy keeps any saved creation cause visible and directs absent-reservation investigation to an event admin.

Regression fixtures cover error-code/status distinctions, adversarial diagnostics, uncertain responses, credential/origin binding, bounded bodies, repeated retries, restart persistence, unchanged identity/Git history, and eventual same-Sprite reconciliation. Browser fixtures cover cause/absence text, explicit retry, reload without automatic retry, keyboard/touch access, phone/desktop/short viewports and both themes. Fixtures do not contact Sprites or paid models; physical-device and live deployment acceptance remain separate.
