# Workspace provisioning errors

Token-configured installations create Sprites through one authenticated HTTPS `POST /v1/sprites`, using the configured API origin and the token's validated organization. The response must identify the requested name and organization. There is no automatic POST retry, redirect, or CLI fallback after an ambiguous result. Command and lifecycle admission remain bounded; checkout and participant execution still use the existing CLI inside the reserved Sprite.

Local installations with only a saved CLI login retain the pinned `create --skip-console` path. Free-form stderr is not a structured provider contract: CLI failure is sanitized to unknown, even if its text mentions a limit, HTTP status or credential. No error body, stdout, stderr, provider message or upgrade URL is persisted or returned to the browser.

The [official Go SDK error schema](https://github.com/superfly/sprites-go/blob/main/errors.go), checked 2026-09-17, supplies `error` as a string, with separate `concurrent_sprite_limit_exceeded` and `sprite_creation_rate_limited` codes. The adapter consumes those exact codes from a bounded JSON response. The first means provider capacity, including concurrent active-workspace restrictions; it does not identify a particular running/warm/total quota. The second means creation throttling. No separate running/warm error codes or prose patterns are invented. Both may use HTTP429; an unknown structured code remains unknown. Bare429 gets a generic request-limiting message. HTTP401/403 indicate access denial; HTTP408/5xx and transport failures indicate a connection/service failure with an uncertain creation outcome. Successful HTTP with malformed, oversized or mismatched identity data also remains uncertain.

The provider's [API reference](https://sprites.dev/api/sprites) documents creation, named-resource GET and list metadata's `running_limit`/`warm_limit`. Limit values or resource counts alone do not establish why an earlier creation failed. This change does not assert quota for any historical incident whose original diagnostics were discarded.

`spriteCreationFailure` stores only an optional allowlisted category in the existing workspace state. Domain writes preserve the first observed category through phase changes, retry failures and restarts. A later POST failure shows its sanitized current category alongside the original cause. Successful preparation clears it. Legacy records receive no inferred cause. If recording an error fails, the already-persisted reservation still prevents an automatic second allocation; the lost cause cannot be reconstructed.

A failed reconnect may perform a bounded metadata GET for the exact reserved name. Only authenticated HTTP404 establishes current absence; access errors, timeouts, malformed responses and identity mismatches remain unknown. Absence alone does not authorize creation. Current failure copy keeps any saved creation cause visible and directs absent legacy-reservation investigation to an event admin.

## Explicit initial-creation retry

For new token-configured reservations, EventService writes an `initial_sprite_creation` record in `state.sqlite` before the first reservation/POST. It binds the workspace UUID and canonical Sprite name to the configured HTTPS provider origin, organization slug and a hash of the credential's organization/account ID. It stores no token or private contents and is not exposed in participant responses. Token rotation within the same provider account is supported. CLI-login-only and legacy reservations do not acquire this evidence retrospectively.

The record becomes permanently sealed before checkout, verification or ready can be saved. This separate durable write precedes the phase write, so a crash or a later retry that rewinds the visible phase cannot reopen eligibility. Only a still-creating record with the initial bundling/creating phase may use explicit **Retry preparation** to retry initial creation. The browser sends `action: "retry-initial-creation"`; ordinary open, wake, polling, reload and server startup do not request it.

The retry rechecks owner session/membership, event access, workspace/event generations, lifecycle gates and provider binding after an exact-name GET and again at actual queued POST dispatch under the existing lifecycle lease. A confirmed404 permits one POST for the same reserved name; unknown GET results never permit a POST. A provider conflict or uncertain POST has no automatic fallback or replacement. Concurrent requests share the existing bounded provisioning job. Before seeding an existing resource, preparation seals eligibility and checks that the project is absent (including dangling symlinks); the checkout script checks again and preserves any existing project. A ready/private-checkout reservation is never eligible for this retry path.

## Legacy operator recovery boundary

A legacy `error/creating` phase and a present-day404 cannot prove that a workspace never became ready: retries rewind phases, and activity entries use display names rather than immutable workspace IDs. Do not backfill initial-creation evidence, reset reservation state or invent a historical cause from those observations.

The existing targeted recovery procedure is **Admin → Sprites → Delete** for the exact workspace, including its explicit private-data-loss confirmation, followed by that workspace owner's explicit reopen. The validated deletion action accepts a provider204/404, retains the original reservation, and authorizes a fresh same-name existence check and recovery from canonical shared Git. It can delete a resource that appears before the request, so it is a separately authorized destructive recovery action, not an initial-create retry or a harmless metadata check. This work does not invoke it. See [individual deletion](sprite-lifecycle.md#individual-deletion). If preserving unknown historical private work is required, stop at investigation; no local management receipt can reconstruct missing Sprite-private files. For an actual restored installation, use the separately fenced [backup/restore reconciliation](backup-restore.md); do not manufacture its recovery receipt on a live installation.
