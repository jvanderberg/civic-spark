# Workspace provisioning errors

Token-configured installations create Sprites through one authenticated HTTPS `POST /v1/sprites`, using the configured API origin and the token's validated organization. The response must identify the requested name and organization. There is no automatic POST retry, redirect, or CLI fallback after an ambiguous result. Command and lifecycle admission remain bounded; checkout and participant execution still use the existing CLI inside the reserved Sprite.

Local installations with only a saved CLI login retain the pinned `create --skip-console` path. Free-form stderr is not a structured provider contract: CLI failure is sanitized to unknown, even if its text mentions a limit, HTTP status or credential. No error body, stdout, stderr, provider message or upgrade URL is persisted or returned to the browser.

The [official Go SDK error schema](https://github.com/superfly/sprites-go/blob/main/errors.go), checked 2026-09-17, supplies `error` as a string, with separate `concurrent_sprite_limit_exceeded` and `sprite_creation_rate_limited` codes. The adapter consumes those exact codes from a bounded JSON response. The first means provider capacity, including concurrent active-workspace restrictions; it does not identify a particular running/warm/total quota. The second means creation throttling. No separate running/warm error codes or prose patterns are invented. Both may use HTTP429; an unknown structured code remains unknown. Bare429 gets a generic request-limiting message. HTTP401/403 indicate access denial; HTTP408/5xx and transport failures indicate a connection/service failure with an uncertain creation outcome. Successful HTTP with malformed, oversized or mismatched identity data also remains uncertain.

The provider's [API reference](https://sprites.dev/api/sprites) documents creation, named-resource GET and list metadata's `running_limit`/`warm_limit`. Limit values or resource counts alone do not establish why an earlier creation failed. This change does not assert quota for any historical incident whose original diagnostics were discarded.

`spriteCreationFailure` stores only an optional allowlisted category in the existing workspace state. Domain writes preserve the first observed category through phase changes, retry failures and restarts. A later POST failure shows its sanitized current category alongside the original cause. Successful preparation clears it. Legacy records receive no inferred cause. If recording an error fails, the already-persisted reservation still prevents an automatic second allocation; the lost cause cannot be reconstructed.

A failed reconnect may perform a bounded metadata GET for the exact reserved name. Only authenticated HTTP404 establishes current absence; access errors, timeouts, malformed responses and identity mismatches remain unknown. Absence alone does not authorize creation. Current failure copy keeps any saved creation cause visible and offers explicit owner recovery for missing legacy reservations.

## Sanitized create diagnostics

Each dispatched token-authenticated create POST emits one bounded `sprite.create` JSON record to the management console; an optional `SpriteClient` logger callback may replace that sink. It includes a SHA256 hash of the reserved name for correlation, the guarded-create flag, HTTP status if headers arrived, total duration, and separate header/body/validation/abort elapsed milliseconds measured from POST dispatch. Abort kind and stage distinguish a timeout waiting for headers from a timeout reading the body, or lifecycle cancellation. Missing timestamps mean that stage did not complete. Failure categories and confirmation reflect existing behavior, without changing status or identity acceptance.

Response diagnostics contain only fixed field types and exact requested-name/configured-org/token-account equality booleans. No raw name, organization/account identifier, token, response body, provider error text, URL or participant contents is logged. Malformed or oversized JSON yields no decoded field values. A failed logger cannot trigger a retry or change the creation result. Admission failures and metadata-only calls do not emit a create POST record; absence of a record is not evidence of resource absence. The historical POST status/body cannot be recovered by enabling this observer later.

## Provider metadata identity

Recovery and provisioning share one metadata contract. The [current API](https://sprites.dev/api/sprites) defines List's top-level `name` as the authenticated organization slug. When present, it must match the configured organization and validated token; unrelated List rows do not establish the reserved resource's ownership. The [official JavaScript SDK](https://github.com/superfly/sprites-js/blob/main/src/client.ts) accepts a null list; Civic Spark accepts that shape only with a matching explicit organization identity. Older rc48 responses without top-level `name` still require an array and matching optional row claims. Malformed shapes and conflicting top-level identity remain unknown. Responses are bounded and their diagnostics are not exposed.

The provider also documents resource `organization` as a slug. A live unrelated List row contradicted its matching top-level organization identity during the September 17 recovery exercise; that alternate value's meaning remains unexplained. It is not treated as an accepted ID or alias. Before any named GET or guarded create, List rows matching the reserved name must also have nonconflicting ownership claims, including every duplicate target row. A matching top-level identity cannot override a target-row conflict, even if the subsequent named GET would return404. Named GET and create still require the exact reserved name and configured `organization`, and reject any conflicting `org_slug`. An authenticated List cannot override a named resource mismatch or turn an uncertain GET into permission to create. These checks do not change owner authorization, leases, generation checks, recovery receipts or preservation of existing private work.

## Explicit initial-creation retry

For new token-configured reservations, EventService writes an `initial_sprite_creation` record in `state.sqlite` before the first reservation/POST. It binds the workspace UUID and canonical Sprite name to the configured HTTPS provider origin, organization slug and a hash of the credential's organization/account ID. It stores no token or private contents and is not exposed in participant responses. Token rotation within the same provider account is supported. CLI-login-only and legacy reservations do not acquire this evidence retrospectively.

The record becomes permanently sealed before checkout, verification or ready can be saved. This separate durable write precedes the phase write, so a crash or a later retry that rewinds the visible phase cannot reopen eligibility. Only a still-creating record with the initial bundling/creating phase may use explicit **Retry preparation** to retry initial creation. The browser sends `action: "retry-initial-creation"`; ordinary open, wake, polling, reload and server startup do not request it.

The retry rechecks owner session/membership, event access, workspace/event generations, lifecycle gates and provider binding after an exact-name GET and again at actual queued POST dispatch under the existing lifecycle lease. A confirmed404 permits one POST for the same reserved name; unknown GET results never permit a POST. A provider conflict or uncertain POST has no automatic fallback or replacement. Concurrent requests share the existing bounded provisioning job. Before seeding an existing resource, preparation seals eligibility and checks that the project is absent (including dangling symlinks); the checkout script checks again and preserves any existing project. A ready/private-checkout reservation is never eligible for this retry path.

## Explicit owner recovery of missing workspaces

Legacy reservations never acquire initial-create evidence retroactively. A failed owner workspace instead offers **Rebuild from shared work**, with explicit confirmation that only canonical shared team Git is recoverable and unshared files, commits and workspace history are unavailable. Cancel, status polling, reload and ordinary wake do not authorize recreation. Existing initial-create retry and administrator deletion/reopen remain separate operations.

The confirmation sends only the action, expected name/generation and acceptance of shared-work recovery. The server authenticates the current provider organization and requires a fresh exact-name HTTP404. EventService validates owner access, event/lifecycle generations, reservation identity and the server's bounded-age evidence before recording an `ownerRecovery` qualifier on the existing durable deletion/replacement state. This records present-day absence, not historical deletion or evidence that creation never completed. It retains the same workspace UUID, team, reserved name and shared Git source, and reserves the replacement slot. No provider DELETE occurs.

Creation checks authenticated organization and exact-name absence again after command-queue admission under a lifecycle lease. Owner session/membership, event state, generation, deletion marker and provider origin/org/account binding are checked after async inspection and immediately before POST dispatch. Only a validated201 for the requested name/org permits checkout; present resources, mismatched/malformed data, auth/network errors, ambiguous200 and conflicts stop the operation. There is one POST with no automatic retry or fallback. Authorization is checked again before checkout, at queued upload dispatch and after verification. Checkout retains its existing protection against overwriting an existing project.

Only canonical shared main seeds recovery, never the private management checkout. The marker remains through partial/uncertain failure and restart; later attempts require another owner confirmation. If an existing resource is found on retry, it is preserved without inspection of private files or upload, even if a previous POST might have created it. An operator may need to reconcile that ambiguous present resource; absence alone cannot reconstruct lost private state. The older explicitly destructive admin Delete/reopen and separately fenced backup/restore contracts remain unchanged.
