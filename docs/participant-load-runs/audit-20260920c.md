# Civic Spark management-host load audit (read-only, 2026-09-19/20)

Scope: every path where the management host does work per participant or per poll. Audited at commit da21691 plus the uncommitted work in worktree `sweet-chipmunk` (see "Baseline"). Read-only: no source edits, no hosted or paid operations. Measurements are from `REPORT.md`/`backend.jsonl` in this directory (50-person run) and from local micro-benchmarks run against the repository's own modules (noted as "measured"); everything else is an estimate with the arithmetic shown.

## Baseline: what is already changed in this worktree (not duplicated below)

The working tree already contains, uncommitted (verified with `git diff`):

- Portal state slimmed (`portal()` strips project `description`; briefs via `GET /api/events/:id/projects/:projectId`), weak ETag + 304 and Brotli/gzip for API bodies (`apps/server/src/response-encoding.ts`), precompressed immutable static assets (`app.ts:996-1013`), client conditional GETs (`apps/web/src/api.ts`), portal poll 15 s and paused while hidden (`App.tsx:140-155`).
- Agent text deltas merged per message for 50 ms before replay/fan-out, and activity touches throttled to one per second per workspace (`apps/server/src/agents.ts` diff).
- File polling 20 s when the agent is idle, 5 s while working, none while hidden (`Workspace.tsx:216-235` diff); preview status 1 s while launching, 10 s while the agent works, else 30 s (`EnvironmentControls.tsx:52-66` diff).
- Loop telemetry: a `loop` diagnostic every 10 s with event-loop delay p50/p99/max, CPU share, handle/child/socket counts, RSS; `bytes` per HTTP response (`apps/server/src/diagnostics.ts:51-83`).

All cost estimates below assume that baseline. "@60" means 60 participants with the workspace open and visible, of whom ~20 have an agent turn running and ~20 have the terminal tab mounted (it stays connected while other tabs are shown).

## 3. Per-finding detail

### F1. Long-lived helper session per Sprite (highest structural leverage)

Today every read poll is a fresh Sprite CLI process: `client.ts:191` `execFile("sprite", [-o org, -s name, exec, --no-port-forward, --, python3, -c, <whole script>])` with the JSON request written to stdin (`client.ts:198`) and the answer read back and zod-validated (`client.ts:644-661`). The CLI is a 16 MB binary that opens its own authenticated session per call (p50 192 ms, p95 463 ms of execution in the run). The in-flight coalescing (`client.ts:581-597`) only merges identical requests that overlap, which happened 9 times in 5,178 commands. `CommandQueue` (16 slots) bounds concurrency but not frequency.

Per participant today (post-baseline): files + changes + open file every 5 s while the agent works (else 20 s), preview status every 10/30 s, team status every 15 s, plus one-off `credential-presence.py`, `setup.sh`, and the relay. @60 with 20 active agents: 20 x 3/5 + 40 x 3/20 + 20/10 + 40/30 + 60/15 = 12 + 6 + 2 + 1.3 + 4 = ~25 spawns/s. Loop cost per spawn is unmeasured here; libuv on Linux forks the (large) Node process on the loop thread, sets up three pipes, and tears down on `close`; 2-6 ms each gives 50-150 ms/s, plus TLS/WebSocket setup inside each child (CPU on the same 2-vCPU Machine) and the observed 18 concurrent children.

Proposal: one persistent `sprite exec` per Sprite running a small JSON-lines helper (the same shape as `packages/agents/runtime/relay.py` and the agent runner: newline-delimited requests on stdin, responses on stdout, `id` correlation). It serves `list`, `changes`, `read`, `save`, `manifest`, `blob read/mutate`, `preview status/logs`, `team status`, `credential-presence`, and can host the relay's spool loop. Host side: `SpriteClient` gets a `session(name)` that lazily spawns, multiplexes requests with the existing per-operation zod schemas and timeouts, and falls back to the current one-shot path when the session is absent (Sprite asleep, held, or after an error). Keep `share`, `import`, `apply`, `start/restart` as one-shot commands initially (they are rare and long).

Constraints:
- Security boundary unchanged: the helper is trusted only as much as `files.py` is today (it runs as the Sprite user; participant or agent code could alter its files on disk). Send the helper source through `--file` or stdin at spawn (as today for scripts), keep all path/size validation on both sides, and keep zod validation of every response on the host. Participant code still never runs on the host.
- Lifecycle: acquire a passive lease (`client.lease(name, true)`) like the relay so the session never counts as activity and `lifecycle.disconnect` kills it on hold/pause; `releaseIdle` (`lifecycle.ts:84-108`) stays authoritative. Idle release must terminate the helper so the Sprite can hibernate; provider docs say a quiet exec session is activity, so the helper must not busy-poll (relay.py's 250 ms loop should become inotify/blocking reads when merged).
- Generation and wake: key the session by `{spriteName, runtime.generation}`; drop it on `setRuntime` generation changes, on `sprite exec` exit, and when the provider reports sleep. A request against a dead session falls back to one-shot once, then respawns.
- Backpressure: bound in-flight requests per session (e.g. 4) and keep the 30 s per-request timeout; responses above 16 MiB still rejected.
- Diagnostics: keep `sprite.operation` records; add `session_reused` outcome.

Effort L (client session multiplexer, helper merge of four scripts, tests in `tests/sprite-*.test.ts`, lifecycle race tests). Expected: spawns/s from ~25 to ~0.2 (respawns), loop work from 5-15 % to <1 %, wall latency per poll from ~200 ms to ~20 ms.

### F2. Bridge process for agent, terminal and relay streams

`agents.ts:153-186` spawns a `sprite exec ... node runner.ts` per workspace and reads its stdout through `readline` (`agents.ts:216`), then fans out to WebSocket clients (`agents.ts:229-233`, now batched). `terminal.ts:45-50` spawns a PTY per workspace and forwards every chunk (`terminal.ts:60-75`). `integrations.ts:95-133` spawns a relay per prepared workspace. All of these are pipe reads, JSON parsing, string handling and WebSocket writes on the main loop. @60 that is up to 140 children and, from section 1, roughly 100-200 ms/s of loop time before F3.

Proposal: a single `child_process.fork` bridge that owns those children and the WebSocket sessions. Fastify's `websocket: true` handlers (`app.ts:682-743`) authorize as today and then hand the raw upgraded socket to the bridge with `subprocess.send({kind:"agent", id, sprite, ...}, socket)` (Node supports passing `net.Socket` handles); the bridge completes the `ws` handshake (`WebSocketServer.handleUpgrade`) and runs the current `AgentSessions`/`TerminalSessions` logic unchanged. The main process keeps `lifecycle`, `service`, `auth`; authorization checks (F10) become IPC messages, and `lifecycle.disconnect`/`stop` become `{kind:"stop", id}` messages. `AgentSessions.isWorking`/`isPreparing`/`recentlyUsed` become bridge-reported state mirrored in the main process (push on change).

Constraints: single-writer SQLite stays in the main process (the bridge never opens the DBs); leases (`lifecycle.acquire`) stay in the main process and are requested over IPC before spawn; graceful shutdown must close bridge children (`app.ts:245-253`). Provider secrets: the bridge inherits `SPRITE_TOKEN`/org env like today's children; no new exposure. Tests need an in-process mode (bridge as a module) so `tests/agent-*.test.ts` keep working.

Effort L. This is the only item that uses the second vCPU without cluster mode (cluster is not an option: sessions, leases, `sharing` and provisioning state are in-memory maps).

### F3. Terminal output handling

`terminal.ts:63-67` rebuilds a 200 KB string per PTY chunk (measured 0.233 ms per 512 B chunk). tmux redraws its status line and TUIs such as the Claude Code CLI redraw spinners many times per second whether or not a browser is attached; the PTY bridge is only killed by idle release (`lifecycle.ts:100-106`) after five minutes without participant input, and product docs already promise that terminal output is not activity (`docs/sprite-lifecycle.md:46`). With 20 terminals emitting 10-30 chunks/s that is 50-150 ms/s.

Proposal: (1) keep `history` as an array of `Buffer`s with a running byte total, trimming whole chunks past 200 KB; (2) strip `\x1b[6n` and `\x1b]11;?...` from the incoming chunk only, carrying the last 16 bytes across chunk boundaries; (3) coalesce output per session with a 16 ms timer before `send` (xterm.js renders per animation frame anyway); (4) when `clients.size` drops to 0, start a 30 s timer and then kill the PTY child while leaving tmux running; reattach re-runs `tmux new-session -A` which redraws the screen, so the host history buffer can shrink to a few KB or disappear. Keep `lastUsedAt` semantics (input only) and the 1 MiB `bufferedAmount` guard.

Mobile/UX constraints: reconnection after refresh must still work (tmux provides it); "Terminal detached; reconnect to resume" copy already exists. Effort S/M; tests in `tests/terminal*.test.ts`.

### F4. State cloning on every lookup

`engine.snapshot()` (`engine.ts:89-91`) is `structuredClone(this.state)` and is the only accessor; `service.workspace()` (`service.ts:674`), `provisioningRecords()` (`service.ts:97-99`), `executionAllowed()` (`service.ts:136-145`), `portal()`, `project()`, `canJoin()`, `siteEvent()` all call it. A single `GET /api/workspaces/:id/files` clones the state ~7 times (`app.ts:380` workspace, `:383` executionAllowed, `:388` acquire = `lifecycle.ts:110` + `:112`, `app.ts:777` workspace, `client.ts:184` acquire again x2). Every WebSocket `check` clones 2-3 times (`app.ts:703-705`). Measured 0.27 ms per clone at 310 KB; the deployed state during the run was at least the 235 KB portal payload plus contributions and an activity log that only grows (`engine.ts:109`, no cap). @60: ~40 req/s x 7 + 20 checks/s x 2.5 = ~330 clones/s = ~90 ms/s, and it scales with rooms that keep creating teams.

Proposal: give the engine indexed read-only accessors (`participant(id)`, `team(id)`, `event(id)`, `participants()`), returning frozen references or shallow copies of the single record; keep `snapshot()` only for backup and `portal()`. Add a `version` counter bumped in `save()` so `portal()` can memoize the built body per actor id and version (the ETag then hits without rebuilding). Cap `activity` at a few hundred rows (it is admin-only output). `runtime()`/`execution()` re-prepare SQL statements on every call (`service.ts:101, 105`); cache prepared statements (6 us each today, so minor).

Constraints: `service.workspace()` currently returns spread copies; callers do mutate the returned objects in some paths (`provisioning.ts:59`) so return fresh shallow copies of the record, never internal references. Effort S/M with tests already covering the service layer.

### F5. Activity persistence

`lifecycle.touch` (`lifecycle.ts:72-75`) calls `executionAllowed` (one clone, two SQLite reads) and `setRuntime` (one read, a JSON compare, an `INSERT ... ON CONFLICT` commit). SQLite is in WAL mode with default `synchronous=FULL` (verified: nothing sets the pragma; `PRAGMA synchronous` returns 2), so each commit fsyncs the WAL. Locally 0.1 ms; on a Fly volume expect 0.5-3 ms. Before the baseline this ran once per text delta (300-400/s) and is the most likely single source of the "native I/O" the profile could not attribute (1.5 GB written, 0.57 M write syscalls over the run is consistent with ~950 small writes/s). The baseline throttles agent touches to 1/s per workspace; terminal input (`terminal.ts:129`) and the 30 s browser activity POST (`Workspace.tsx:70-83`) also touch.

Proposal: keep `lastUsedAt` in a `Map` inside `WorkspaceLifecycle`; `releaseIdle` reads the map first and falls back to the persisted value; persist every 30-60 s per workspace and immediately on hold/wake/hold-release. Decide separately whether `PRAGMA synchronous=NORMAL` is acceptable for `access.sqlite`, `state.sqlite` and `auth.sqlite` (in WAL mode NORMAL cannot corrupt the database; it can lose the last transactions after power loss, not after a process crash). Effort S.

### F6. Changes payload

`workspace.py:141-168` returns a unified diff for every changed file (200 KB per file, 2 MB total caps) and `Workspace.tsx:178` requests it on every refresh; `Changes.tsx:150-175` renders every diff expanded. While an agent edits, the body changes every poll so ETag/304 does not help. On the host the body is `JSON.parse`d and validated with `changesSchema` (`client.ts:644-654`), stringified, sha1-hashed (`response-encoding.ts:24`) and Brotli-compressed on the threadpool (the Machine has two vCPUs, so the threadpool competes with the loop). At 500 KB that is ~5 ms of loop time per poll; at 20 people polling every 5 s that is 20 ms/s plus tens of ms of compression CPU.

Proposal: `changes` returns a summary (`path`, `status`, `binary`, `size`, `diffBytes`, plus `base`/`revision` unchanged); add `GET /api/workspaces/:id/changes/diff?path=&revision=` served by the Sprite (one file); the client requests diffs for files whose `<details>` are open (default open the first N, lazily load the rest, keep loaded diffs keyed by `revision`). Share continues to send `revision` (`Changes.tsx:54`), so the safety check `workspace.py:173` is unchanged. Mobile: fewer bytes and less DOM per poll help phones directly. Effort M (helper op, route, client, `tests/changes*.test.ts`, browser smoke).

### F7. Team status

`team-updates.ts:41` calls `service.teamReferenceAsync`, which runs `git rev-parse main` in a child process (`service.ts:726`), before checking the 10 s cache at `:46-53`. Every 15 s poll therefore spawns git even when the cached status is returned: 602 spawns in the run, 4/s @60. Proposal: maintain `mainHead` per team in memory, set by `engine.publishPrepared`, restore, copy and team-update completion (all in-process), verified lazily with one `rev-parse` when the cache is empty; check the status cache before any I/O. Effort S.

### F8. Synchronous git on the loop

`packages/git/src/repository.ts:17-41` uses `spawnSync`; `history.ts:66-90` runs `rev-list` then `git show -s` per commit (31 processes per page), `repositoryVersion` runs `ls-tree` plus `cat-file -s` per large file, `repositoryFile` runs `cat-file`/`diff`. `engine.exportTeam` (`engine.ts:672-676`) runs `git archive --format=zip` synchronously and buffers the whole ZIP. Each `spawnSync` blocks the loop for the process lifetime (3-10 ms for trivial git commands on a warm cache; more under load), so a history page stalls everyone for 100-150 ms; 167 pages were loaded in the run. Proposal: `gitAsync` everywhere in read paths; one `git log --format=... -z --max-count=31 --skip=N` instead of per-commit `show`; stream `git archive` (`spawn` + `reply.send(child.stdout)`, with `Content-Length` omitted); admin restore paths can keep `spawnSync` (rare) or move to `gitJob`. Effort S.

### F9. Portal polling

`App.tsx:95-125` `refresh()` awaits `/api/session` and then `/api/state`; the 15 s timer (`App.tsx:140-155`) runs whenever a user is signed in, including while a workspace is open (the workspace is rendered from `state.myWorkspaces`). `/api/session` (`app.ts:338-347`) clones state for `siteEvent`; `/api/state` (`service.ts:429-508`) calls `remember()`, clones, builds the per-actor view, and the encoder hashes it even when the answer is a 304. In the run `/api/session` was the single most frequent route (2,833). @60: 8 req/s, ~1.5 ms each, ~12 ms/s; not large now, but it is the one path whose work grows with teams x people.

Proposal: fetch `/session` on load, after sign-in/out and on 401 only; add a state version (bumped in `engine.save()`/`service.save()`/`setRuntime` for that actor's workspaces) exposed as a tiny `GET /api/state/version` (or as a header on `/state`) and fetch the body only when it changed; inside a workspace poll only the version. Later, F2's bridge can push `stateVersion` on the agent socket, removing the poll entirely for connected users. Effort S/M.

### F10. Authorization cadence

Agent sockets (`agents.ts:279`), terminal sockets (`terminal.ts:116`) and relays (`integrations.ts:122-131`) each re-run `authorized()` on a timer: `getSession` (0.25 ms measured) + `service.workspace` + `allowed` (two clones). HTTP runs `getSession` per request (`app.ts:205`) and the workspace routes then clone several times (F4). @60: 60 agent + 20 terminal sockets / 5 s + 60 relays / 15 s = 20 checks/s; ~26 ms/s in total with HTTP. Proposal: 30-60 s periodic revalidation plus event-driven closes: sign-out (`app.ts:254-283` can call `agents.stopUser`/`terminals.stopUser` for that user id), `removeMember`/`removeEventMember`/`deleteTeam` (service events), pause/hold (already `lifecycle.disconnect`). An optional 5 s positive `getSession` cache keyed by a hash of the cookie, purged on sign-out, removes most HTTP auth work; revocation latency would then be at most 5 s, which should be documented in `docs/product.md` if adopted. Effort S.

### F11. Agent prepare and credential checks per connect

`Agent.tsx:370-401` runs `GET .../agent/credentials` (a `sprite exec python3 -c credential-presence.py`, `agents.ts:70-84`) and `POST .../agent/prepare` on every connect and reconnect; `Terminal.tsx:145` also posts `prepare`. `prepare` (`agents.ts:115-139`) executes `setup.sh` with 13 `--file` uploads; `setup.sh:11-22` runs both CLIs' `--version` and a `node` import check every time even when `.installed` matches (several seconds of Sprite CPU, billed). The runner spawn (`agents.ts:161-179`) uploads 11 source files each time. Proposal: memoize preparation per `{sprite, generation, sourceFingerprint}` in `AgentSessions` while the runner or relay child is alive (or for 30 min), so a second tab, the terminal, or a reconnect skips `setup.sh`; in `setup.sh` record verified versions next to `.installed` and skip the slow `verify()` when the fingerprint matches; serve `credential-presence` from the F1 helper. Constraints: never skip after a generation change, reset or wake-from-error; keep runtime setup on the committed scripts only (AGENTS.md). Effort S/M.

### F12. Replay volume on reconnect

`agents.ts:258-260` sends every retained event as its own frame (`historyLimit` 500 events / 10 MiB, `history.ts:3-4`), and each runner start replays its journal through stdout (`runner.ts:626-627`) where the host parses, validates and retains it again. After a deploy or a mass wake, 60 reconnects can push hundreds of MB through the loop, and the `bufferedAmount > 12 MiB` guard (`agents.ts:230`) then closes sockets with 1013, prompting the client's retry (`Agent.tsx:551-560`) and another replay. Proposal: one `{type:"replay", events}` frame per attach (the client already merges with `retainEvent`, `Agent.tsx:529-533`; keep the T3 UI untouched), a 1-2 MiB replay cap with older history fetched on demand, and journal replay accepted as a single array. Effort M; protocol change needs `packages/agents/src/protocol.ts` and client tests.

### F13. Local folder sync

`LocalSync.tsx:105` refreshes every 5 s; `folder-sync.ts:133` fetches `manifest`, which reads and hashes every project file in the Sprite (`workspace.py:65-88`) and returns up to 5,000 entries. Desktop-only, but each connected user is one spawn per 5 s plus a large JSON body. Proposal: the Sprite returns a tree revision; the client passes its last known revision and receives `{unchanged:true}`; 10-15 s idle interval with immediate refresh on `onUpdated`. Effort S/M; folds into F1/F15.

### F14/F15. Preview status and in-Sprite recomputation

`preview.py:180-212` runs `sprite-env services list` and an HTTP probe per status call; `files.py:46-62` walks the tree per `list`; `workspace.py:95-138` hashes every file and runs `git hash-object` per changed candidate per `changes`. These cost Sprite CPU (billed) and 200-460 ms of wall time per poll, and the host waits on all of it. Inside the F1 helper these become cached computations keyed by directory mtimes (or inotify), returning `{unchanged:true, revision}` when the client's known revision matches, which also lets the HTTP layer answer 304 without any host parsing. Until F1: read `preview-state.json` directly while `installing` (skip `services list`), and poll 3 s rather than 1 s during launches (`EnvironmentControls.tsx:57-60`).

### F16-F18. Small host-side items

- `client.ts:608` and `:709-711` read the helper script and `environment.json` from disk on every Sprite command, and `agents.ts:74-77` reads `credential-presence.py` per check; read once at module load (S).
- Diagnostics (`packages/diagnostics/src/index.ts:112-127`): per-record zod + stringify + synchronous stdout write. ~0.3 % @60; fine, but a stalled log consumer would block the loop. Consider aggregating `http` records per route per 10 s when `loopP99Ms` exceeds a threshold (S).
- Share (`app.ts:858-859`, `integrations.ts:380-383`): the bundle travels as base64 inside JSON (up to 14 MB) and is re-encoded for comparison synchronously; 30-60 ms per share at 10 MB. Cheap fix: length check plus chunked base64 validation; better: transfer the bundle as a file rather than through JSON (S).

## 4. Browser to Sprite directly: assessment

Preview traffic already bypasses the host (native `*.sprites.app` URL made public at Launch; `client.ts:80-157`, `docs/portability.md` "Public preview adapter"). Moving files, agent or terminal traffic to a Sprite-hosted service is not recommended now:

- The only browser-reachable Sprite endpoint is the public preview URL, which serves whatever the participant runs on the configured port; private files or agent sessions behind it would be protected only by an application token that participant code in the same Sprite can read. Admin/event gating, session revocation and pause holds are enforced by the host (`app.ts:368-390`); `docs/portability.md` states direct public requests intentionally bypass them.
- The organization token must never reach the browser (`client.ts:79`), so authenticated Sprite API access from the browser is out.
- Direct browser polling would be provider activity and keep Sprites awake and billed, contradicting the idle policy (`docs/sprite-lifecycle.md:46`) and the memory note that helper GETs wake Sprites.

Revisit only with: a per-workspace capability token minted by the host with short expiry, a second authenticated origin/port distinct from the preview service, explicit wake/billing semantics, and event-gate enforcement inside the Sprite. That is a security design, not an optimization.

## 5. What must not change

- Participant-generated code never executes on the management host; helpers, relays and any new daemon run inside the Sprite, and the host validates every response (AGENTS.md; `docs/product.md:120`).
- Publication rules: Share is the user's explicit action; agents publish only after explicit confirmation for the current changes; conflict resolution needs an owner-confirmed ticket; polling and pulling never publish (`integrations.ts:322-419`, `team-updates.ts`).
- Idle and billing behavior: five-minute release of platform polling; terminal output is not activity; passive leases for bridges; polling never wakes or recreates Sprites; `releaseIdle` remains authoritative; explicit Stop/Pause semantics unchanged.
- Security boundaries: all APIs require a session; no request-supplied identity; admins cannot read another person's private files; credentials stay out of project files, exports, logs and browser responses; org token never browser-visible; `sprite`/`wake` are the only routes that bypass the execution gate.
- Mobile requirements: every UI change (Changes lazy diffs, terminal detach copy) verified at 360/390 px, desktop and short viewports, both themes, with `npm run check` and `npm run test:mobile`.
- Upstream T3 chat UI fidelity and attribution: replay batching must not alter rendering, per-turn rows or add chat UX.
- Reopen/refresh reattaches existing agent context and conversation; provider session IDs are never erased by a bridge or daemon change.

## 7. Open questions

1. Fly volume fsync latency: is `synchronous=NORMAL` acceptable for the three SQLite stores (WAL keeps them corruption-safe; only the last transactions before a power loss are at risk)? This decides how much F5 matters after the throttle.
2. Is a 5 s process-local positive session cache acceptable given "all APIs require a session"? Revocation would lag by at most 5 s; sign-out can purge synchronously.
3. Should the F1 helper source be uploaded per spawn (immune to on-disk tampering for the process lifetime, like today's `-c` scripts) or installed by `setup.sh` (faster respawn)? Recommendation: upload per spawn.
4. Does a persistent exec session count as provider activity and prevent hibernation? Idle release kills it after five minutes, but the memory note ("services/exec/checkpoints GETs wake sprites") suggests verifying with a dedicated civic-spark Sprite before relying on it during quiet periods.
5. Replay cap: what history length must the T3-style UI show on reconnect without a "load earlier" affordance? If a follow-up fetch is acceptable, F12 can cap replay at ~1 MiB.
6. Does the Fly deployment keep stdout as a pipe to the log shipper? If so, F17's non-blocking writer matters more than its CPU cost.
7. Would organizers accept a 30 s (instead of 15 s) team-status cadence once Share/publish invalidate the cache immediately? It halves F7's residual Sprite work.
