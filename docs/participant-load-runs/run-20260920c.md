# Fifty concurrent scripted participants — 2026-09-20 03:43 UTC (bottleneck run)

Deployment: commit 5772c6d, same Machine d8d962e3b65118 (performance-2x, 2 vCPU, 4 GB) and volume, `CIVIC_SPARK_MAX_PROVISIONING=5`, diagnostics on. Instance cleaned beforehand: 24 Sprites destroyed via admin lifecycle API plus one provider orphan, 36 teams deleted, 16 projects kept. Arrivals staggered 3.5 s apart (sign-in throttle is 20/min per address). Fifty isolated browser contexts across five Chromium processes on the test Mac (10 cores, 32 GB; stayed at 84 % memory free, load ~3).
Evidence: `artifacts/participant-load/cohort-2026-09-20T03-43-58-006Z/`, `backend.jsonl`, `cleanup.log`, this file.

## What happened

- First ~20 people (arrivals over the first 70 s) proceeded normally. From roughly 25 concurrent sessions onward the site became unusable for everyone, including the operator's own browser: home page first byte 34.6 s, `/api/health` 21 s, then 4.7 s, while the app's own handler timings stayed at 100–250 ms (p95 ~1 s). Sign-ins timed out on page load, the portal did not render a newly created team within 30 s, two Shares hit conflicts, one agent wait ended because the workspace was held idle.
- Recovery was spontaneous once failed browsers closed and load fell; health returned to 0.14 s.

Conclusion: the single Node event loop on the management host is the bottleneck. It saturated on native I/O and process management while the second core sat idle; new connections queued in front of the app, so even static files took 20–35 s. Request handlers themselves were not slow.

## Load sources, quantified at peak (03:44–03:47)

1. **Portal state polling.** Every client fetches `/api/state` every 5 s (App.tsx timer). The response is **234,590 bytes, uncompressed** (no content-encoding): 155 KB is the teams list, because each team embeds its full `projectBrief` markdown, and 75 KB is the project list with up to 10 KB `description` each. 4.4 requests/s at peak → ~1 MB/s of JSON serialization and socket writes on the loop, and it grows with teams × participants (quadratic in a room that keeps creating teams).
2. **Per-person helper polling.** files, file, changes, preview, team-status, agent-git every 5 s per person: 26 HTTP requests/s total at peak and **11.9 Sprite CLI spawns/s** (each a fresh `sprite exec` process with pipes read back through the loop; 18 in flight at once).
3. **Agent streaming.** Text deltas are forwarded one event per token chunk: **18,606 events in the peak minute across 17 people (300–400/s)**, each going through readline, JSON.parse, zod validation, replay bookkeeping, JSON.stringify and a WebSocket send. Fifty people would be ~1,000/s.
4. **Terminal PTYs**: 17 tmux sessions streaming redraws through the loop.

Not the cause: Sprite command queueing (p95 8 ms), Sprite API errors (0), provisioning limit (0 × 429 thanks to the stagger), memory, disk, GLM.

## What to change (in order of leverage)

1. Shrink and cache `/api/state`: drop `projectBrief` from team rows and `description` from the project list (fetch on demand), enable gzip/br compression, add ETag/If-None-Match so unchanged polls return 304, and slow the poll to 10–15 s or push changes over the existing WebSocket.
2. Batch agent text deltas: coalesce deltas per message for ~50–100 ms before forwarding to clients and journaling; validate once per batch.
3. Back off per-person helper polling when the tab is idle or nothing changed (files/changes/preview/team-status), and skip polls while the agent is working and already reporting updates.
4. Add loop telemetry so this is visible in real time: a diagnostic record every 10 s with event-loop delay p50/p99, process CPU %, active handles, child-process count, bytes written; plus per-response byte counts.
5. Only after 1–4: consider more vCPUs or cluster mode; today the second core is unused because everything runs on one loop.

Backend during the run: 22,085 diagnostic records; 5,178 Sprite commands all ok; HTTP non-2xx only 3 × 409 Share, 1 × 409 preview, 2 × 423 on a held workspace. Zero 429, 502 or 5xx: the app never rejected anything, it simply could not accept work fast enough. The three Share conflicts happened when the browser's first Share request was answered so late that the retry found shared HEAD already moved; the runner reconciled but the app reported a review requirement.

Every failure is a timeout in front of the app during the saturation window (03:45–03:51). Nobody who reached the agent step before saturation failed there.
